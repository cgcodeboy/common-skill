# 源程序组织

详细设计说明书在 GB/T 8567-1988 第 12 章各节之后，必须有一节「源程序组织」。实现的人只拿着说明书写代码时，目录、文件、类型、函数和变量都按这一节，不许另起一套。

语言以框架设计里已经选定的为准。框架没写语言，就停下来问一句，不要凭本机环境猜。仓库里已经有代码时，先看它的目录是不是下面这份依据；是，就往里面加文件。不是，新文件仍按依据放，不往 `utils` 一类目录里继续堆。不要求这一轮搬走所有旧文件，除非用户明确要求整理。

写目录之前，用浏览器打开该语言那一行的目录依据。说明书里写下文档名和地址。没打开，目录就不许写。

## 目录依据

只用该语言官方文档或它的标准构建工具规定的布局。下表没列出的语言，打开该语言官方构建工具生成的默认布局，写上地址。打不开就停，不要用博客里的分层模板顶上。

| 语言 | 目录依据 | 风格依据 | 不要拿来当标准 |
| --- | --- | --- | --- |
| Go | [Organizing a Go module](https://go.dev/doc/modules/layout)：`go.mod` 在模块根；包是一个目录；对外隐藏的包放 `internal/`；多个命令才用 `cmd/<名字>/` | `gofmt`；[Effective Go](https://go.dev/doc/effective_go)；[Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) | `github.com/golang-standards/project-layout`。它自己写明不是 Go 团队的标准。不要为此建 `pkg/`、`src/`、`api/`、`scripts/` |
| Java | [Maven Standard Directory Layout](https://maven.apache.org/guides/introduction/introduction-to-the-standard-directory-layout.html)：`src/main/java`、`src/main/resources`、`src/test/java`、`src/test/resources`。包名就是目录 | 仓库已有的格式化工具。没有则用 [Google Java Style Guide](https://google.github.io/styleguide/javaguide.html)。一个文件一个公共顶层类型，文件名等于类型名 | 在源码根下再套 `service/impl`、`utils` |
| Kotlin | 与 Java 相同的源集 | [Kotlin coding conventions](https://kotlinlang.org/docs/coding-conventions.html) | 同上 |
| Python | 仓库已能安装且是扁平布局时沿用。新建包装使用 [PyPA src layout](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)：`src/<包名>/`，测试在包外的 `tests/` | [PEP 8](https://peps.python.org/pep-0008/)、[PEP 257](https://peps.python.org/pep-0257/)。格式化用仓库已有工具，没有则用 Ruff | 一个 `utils.py` 收下所有函数 |
| Rust | [Cargo package layout](https://doc.rust-lang.org/cargo/guide/project-layout.html)：`src/lib.rs` 或 `src/main.rs`，集成测试在 `tests/` | `rustfmt`；[Rust API Guidelines](https://rust-lang.github.io/api-guidelines/) | 在 `src/` 下为了分层再建空的 `domain`、`application`、`infrastructure` |
| C# | 仓库已有 SDK 风格就沿用。新建时一库一项目，生产代码在 `src/<项目>/`，测试在 `tests/<项目>.Tests/` | [C# coding conventions](https://learn.microsoft.com/dotnet/csharp/fundamentals/coding-style/coding-conventions)。格式化用 `dotnet format` | 用 partial 把一个类型拆进多个文件来躲避篇幅上限 |

| TypeScript | 语言没有统一目录标准。沿用仓库。新建时采用所选框架官方脚手架的目录，写明框架名和文档地址 | 仓库的 ESLint 或 Biome 配置。没有则采用 typescript-eslint 的推荐规则，并写明版本 | 自造 `components`、`hooks`、`utils`、`services` 四套空目录 |
| C、C++ | 没有 ISO 目录标准。沿用仓库里 CMake 或已有构建文件的布局。新建且没有构建文件时，库源码在 `src/`，测试在 `tests/`，并写明这是构建工具的常见做法，不是语言标准 | C++ 用 [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)，格式化用仓库的 clang-format。C 沿用仓库已有风格；仓库没有时，在说明书里选定一份并给出处，不临时编 | |

业务目录是这一节里允许的例外：它表达说明书里的程序划分，名字用领域词，放在官方布局规定的那个根下面。例如 Go 的 `internal/appointment/`，Java 的 `.../appointment/`。这不是另创一种顶层布局。

## 这一节要写进说明书的内容

1. 语言、目录依据的文档名和地址、风格依据的文档名和地址、格式化工具的命令。
2. 到文件为止的目录树。每个目录一句职责。没有职责的目录删掉。
3. 文件表。每一行是一个文件：只在哪一种变化时才改这个文件、里面有哪些类型和函数、明确不放什么。这句话里若要写「和」或「或者」，文件就还没拆对，继续拆或合并，直到一句话说完。
4. 函数表。每一行是一个函数：所在类型、是命令还是查询、读什么、改什么、不许做什么、调用哪些已经列出的函数。入口函数排在该程序的第一行。
5. 依赖方向：谁可以引用谁。领域里的类型和规则不引用数据库驱动、HTTP 框架和配置框架。只有存储实现引用驱动。入口只组装依赖，函数体里不写不变量。
6. 下面的代码约束。语言规范更严的地方，写成更严的那条，并注明出处。

目录树必须和已经选定的内部分解一致。选了领域模型，就不要再加一套空的 `application`、`infrastructure`、`dto`、`mapper`。选了事务脚本，规则仍放在该程序自己的文件里，不要改口变成三层目录。

## 文件怎么拆

按流程逻辑把步骤标成四类：规则、状态迁移、存储、组装。然后按下面的顺序归文件，不要按层数凑目录。

- 守同一条不变量的规则和状态迁移放在同一个文件，方法挂在拥有这条不变量的类型上。
- 存储单独一个文件。驱动调用只出现在这里。
- 组装单独一个文件。它按流程逻辑调用别人，自己不算业务。
- 两个程序改同一个类型时，仍放在这个类型的文件里。只有这个文件会超过 400 行时，才按程序拆开，不按「一层一个文件」拆开。
- 输入项、输出项可以是没有方法的结构，并放在使用它们的那个程序文件里。不为它们单建 `model` 文件。
- 只为了「看起来分层」而存在的文件，删掉。

## 函数和方法怎么设计

函数表里的每一个函数都要满足这些限制。实现时不得另写一套。

- 入口函数的函数体只保留流程逻辑里的步骤调用和失败返回。字段怎么算、查询怎么写、循环里面的细节，都不进入口。读完入口就知道这个程序在做什么。
- 入口下面的每个函数只做一件事，函数体里的语句处在同一个抽象层。一个函数里既有业务判断又有驱动调用，就把驱动留在存储文件，判断留在拥有不变量的类型上。
- 方法写在拥有该数据或不变量的类型上。其他类型不直接改这些字段。
- 查询不修改状态，名字是名词或谓语。命令的名字是动词，可以返回输出项里的成功或失败。条件更新这种必须同时判断和写入的步骤，是一个命令，不拆成「先查询再让调用者写入」。
- 类型的公开方法只对得上这个类型要守的操作。流程里的中间步骤不公开。
- 接口只在两处出现：调用方要隔开驱动，或已经有第二个实现。不为只有一个实现的类型配一个同名接口。Go 里接口放在使用它的那一侧，不放在实现旁边。
- 一个函数若只是把参数原样交给另一个函数，删掉它，让调用者直接调用。
- 一段代码只被一处使用，又对不上流程逻辑里的步骤名，就留在调用者体内，不单独成函数。
- 函数体先写失败和边界，正常路径不包在 `else` 里。正常路径从上读到下。
- 局部变量说出这一步的角色。不用 `data`、`tmp`、`temp`、`obj`、`info`、`val`、`res` 贯穿函数。
- 连续的几行如果必须靠注释说明它在做哪一步，而流程逻辑里已经有这一步的名字，就收成那个函数。注释只是在复述代码时，删掉注释，不拆函数。

## 代码约束

这些限制连同上面两节一起写进说明书。实现时逐条遵守。

- 不新建这些兜底目录或文件：`utils`、`helpers`、`common`、`shared`、`misc`、`temp`、`base`、`manager`。平台标准库里本来就有的名字除外，例如 Java 的 `java.util`，那不是本单元的目录。
- 一个文件只放一个导出类型，或这个类型的一组操作。禁止一个 `Service` 文件写下本单元全部程序。
- 一个文件不超过 400 行。要超过，就按程序标识符或类型拆开，并改这一节的目录树。
- 一个函数对应流程逻辑里的一个步骤，或对应整个程序的入口。函数体不超过 80 行。语言规范把上限写得更低时，用规范里的数。
- 不为了压进行数，拆出只调用一次、名字不能对应设计步骤的函数。
- 参数不超过 4 个。再多就用该程序输入项里已经命名的结构。不另造一个只为少写参数的平行对象。
- 嵌套不超过 3 层。预期的失败用返回或该语言的标准错误提前离开，不把正常路径包在最里面。
- 不用布尔参数切换两条业务路径。路径不同就分成两个函数，名字写进对照表。
- 类型名用说明书里的领域词。不用 `Data`、`Info`、`Manager`、`Processor`、`Helper`、`Util`、`Obj`、`Tmp` 做类型名。框架规定必须叫 `Handler` 或 `Controller` 的，只出现在入口或适配文件，里面不写重叠判断、版本更新和事务。
- 变量不用单字母，循环下标以及该语言风格文档明确允许的接收者缩写除外。布尔量读出来是谓语。有单位的量用该语言的单位类型，不用裸整数再靠注释说明单位。
- 设计里的阈值（重试次数、超时、锁的范围）是具名常量，不在函数体里写字面量。
- 业务失败使用该程序输出项里的错误。不用 panic、不用拿异常当正常分支、不返回临时拼的字符串。不把错误丢掉。不在返回错误的同时再打一条同样内容的日志。
- 注释只写不变量、事务从哪一步到哪一步、以及为什么不采用被否决的做法。不复述下一行代码。导出的类型和函数用该语言的文档注释。
- 测试放在目录依据规定的位置。测试名对得上测试计划里的用例名。断言的是返回值和持久化结果。只断言某个替身被调用过，不算这条用例通过。
- 格式由该语言的官方格式化工具决定。工具不负责折行时，一行不超过 100 个字符。

## 接着写代码时

用户要求按说明书实现时，只创建文件表里的文件，公开函数只使用函数表里的名字。缺一个文件或一个公开函数，先补进说明书的两张表，写清它只在什么变化时修改、改什么、不许做什么，再写代码。

未列出的私有函数只允许两种：它的名字就是流程逻辑里的一步，或同一段逻辑在这个文件里出现两次。除此之外，把代码留在调用者里。不在实现时补 `utils`，也不把入口函数写成计算、查询和写入堆在一起的过程。
