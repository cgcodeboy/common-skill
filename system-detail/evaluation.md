# 批评

对每个提供的命令核对一遍，不要对架构口号核对：

1. 实现者是否不必猜测错误码、幂等键和提交了哪些表。
2. 不变量的守门是否正好位于所有写入路径都会经过的地方。
3. 两个并发调用是否至少有一个会在条件更新处失败。若会两个都成功，设计是错的。
4. 事务是否短，且不含外部调用和人工等待。
5. 重试是否只覆盖可恢复失败，并且有上限。
6. 架构场景的时间预算拆开之后是否仍然够。
7. 发件箱或同类副作用是否与真相同事务写入，投递失败是否不会撤销已经成立的业务结果。
8. 状态迁移是否和契约里的前置一致。图上有、契约里没有的迁移，删掉。
9. 这次修改有没有偷偷增加数据所有者或部署单元。

实质问题引用走查表的某一行。改名和补「注意并发」这种句子不算改完。

决策需要留下记录时，用短记录：上下文指向场景，方案至少两个，结果一个，变难的事一件，证伪是哪一个计数或哪一种重复请求。没有变难的事，说明还没取舍。

内部最多改两遍。第二遍走查仍失败，就把失败的那一行和它破坏的度量交给用户，不要改第三遍。

用户要求修改时，先判断变化落在契约、不变量、事务还是状态。只重开这些。被取代的做法保留一句「被取代，因为……」，避免下一轮忘了代价。
