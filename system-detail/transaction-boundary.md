# 分解、不变量与事务

三件事分开决定。类名服务于它们，不反过来。

## 内部分解

只留一种主分解。否决至少一种，并指向场景。

| 做法 | 留下 | 否决 |
| --- | --- | --- |
| 领域模型 | 规则和状态迁移集中在少数对象上，应用服务只编排一次事务 | 规则只有一步写入，对象会变成空壳 |
| 事务脚本 | 一个操作就是一段直线过程，规则不会在第二处复制 | 同一不变量已经在两个入口各写一遍 |
| 表模块 | 规则真的跟一张表走，没有跨行的生命周期 | 不变量跨多行，表模块会把规则散进查询 |
| 管道 | 每步是纯变换，副作用只在管道两端 | 中间步骤要读当前持久化状态才能决定下一步 |
| 规则表 | 差异是数据，同一段代码解释规则 | 差异是不同的控制流，表会变成隐式语言 |

依赖方向写清楚：领域规则不调用适配器，应用服务开事务并调用仓库，消息投递读取发件箱而不读取领域对象的私有字段。违反这个方向的类不要出现在图上。

## 不变量放哪

每条不变量写成可检验的判断，并指定唯一的守门位置。两个入口都能改同一份真相时，守门必须在被两者共用的对象里，不能在某个 UI 或某个调用方。

守门位置只选一种：聚合上的行为、提交前的同一段领域函数、或数据库约束。数据库约束适合「一行之内或一个唯一键」的规则。跨行的重叠、额度与生命周期，先由领域函数判断，再用同一事务里的版本更新使判断仍然有效。只用唯一键表达不了的规则，不要假装约束已经守住。

若这条不变量跨越架构划定的两个数据所有者，停止详细设计，写明哪条架构决策守不住。不要在这里引入跨服务事务。

## 事务与锁

一次命令一个事务。事务包含：读取守门所需的版本、再检查不变量、写入真相、写入必须同成同败的发件箱。事务不包含：外部 HTTP、等待人、投递到别的进程、组装界面。

锁或版本必须写到行或文档，不写「对服务加锁」。两个并发命令都可能通过检查时，后提交的那个必须因版本不匹配而失败或重试，不能两个都成功。

乐观版本的做法是：条件更新影响行数为 0 则整事务放弃，调用方或本单元按契约重试。重试次数写死，例如一次。重试仍然冲突就返回契约里的冲突错误，不循环到超时。悲观锁只在架构或场景已经否决乐观做法时使用，并写明锁持有到事务结束、不跨外部调用。

延迟预算：把架构场景的时间上限拆开。外部调用、本事务、失败重试各占多少。加起来超过场景度量，就改路径或退回架构，不把超时写得更短来假装还成立。
