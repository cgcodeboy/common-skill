# 例子

这里的类、表和错误名只用来校准密度。另一个单元要重算不变量和事务，不能把预约版本行抄过去。

下面假定架构已经接受：预约模块与卸货模块在同一个发布单元里；预约库是日历真相；确认写入和「预约已确认」发件箱同一事务；冲突用乐观方式处理并最多重试一次；95% 的确认在 1 秒内返回；已确认预约不丢，卸货侧 5 秒内可见。这些不在详细设计里重选。界面上的时间格和撤销条属于 `/system-interaction`，这里只保证拒绝和冲突在契约里可区分。

## 例子一

**输入**

架构定了预约模块用乐观锁和发件箱。请做确认预约的详细设计，同一月台的时间不能重叠。

### 1. 单元与场景

单元是预约模块里的「确认预约」命令。不是整个仓储系统，也不是卸货模块内部。

继承的场景：

- S1：早高峰确认或拒绝在 1 秒内返回；同一时间窗不会有两张已确认预约。本单元负责检查重叠、提交确认、返回冲突。入口报文的网络时间不算进本事务，假设外部适配最多用掉 300 毫秒，本命令含一次重试要在 700 毫秒内结束。这是假设。
- S2：确认提交之后进程崩溃，预约仍在，卸货最终可见。本单元负责把预约行和发件箱行放进同一事务。投递器失败不得删除预约。

非职责：供应商报文如何解析；卸货如何登记到达；页面如何画冲突；要不要拆成微服务。

### 2. 关注点

| 关注点 | 结论 |
| --- | --- |
| 操作 | 提供 ConfirmAppointment。查询下一空档是同一模块的只读操作，供冲突返回使用 |
| 输入 | 仓、月台、时间窗、供应商、请求号。时间窗结束必须晚于开始 |
| 输出 | 已确认的预约号，或冲突时的下一空档 |
| 错误 | 非法输入、该预约状态不允许、时间重叠、版本冲突重试后仍失败 |
| 幂等 | 请求号。同一请求号再次确认返回第一次的结果 |
| 不变量 | 同一仓同一月台，任意两张已确认预约的时间窗不相交 |
| 状态 | 已请求可变为已确认或已拒绝。已确认不再次确认 |
| 持久化 | 预约表是业务真相。月台日版本表只提供并发令牌，不是第二份日历 |
| 事务 | 见第 3 节。不含报文解析和消息投递 |
| 并发 | 两个确认抢同一月台时，只有一个条件更新成功 |
| 锁的对象 | 版本打在「仓 + 月台 + 日期」一行，不打在单张预约上。打在预约上守不住两张不同预约的重叠 |
| 时间 | 本命令预算 700 毫秒，其中重试最多一轮 |
| 观测 | 已确认重叠对数必须为 0。条件更新失败次数可观察，但不是业务错误 |
| 实现自由 | 私有函数如何拆分不约束 |

重叠不变量跨多张预约。架构若把聚合理解成「一张预约自己的字段」，详细设计不把整本日历装进一个聚合，也不新建一个日历服务。守门放在确认命令的同一事务里：先抢到月台日的版本，再查已提交的重叠，再写这张预约。

### 3. 分解、不变量、事务

主分解是领域模型加一个应用服务。预约对象守住自己的状态迁移。重叠判断是领域函数，输入为候选时间窗和该月台已确认的时间窗列表，应用服务在事务里调用它。否决事务脚本：状态迁移和重叠判断若各写在入口里，拒绝路径和确认路径会复制。否决把整日所有预约当成一个聚合加载：高峰只改一张预约，加载整日所有字段会放大事务，S1 的预算没有这个必要。重叠查询只取时间窗和预约号。

不变量由该领域函数判断，并由月台日版本的条件更新使判断有效。唯一键做不到这件事，因为重叠不是相等。否决只加 `(月台, 开始, 结束)` 唯一约束：8:00–9:30 和 9:00–10:00 并不相等，约束挡不住。

事务顺序：

1. 若请求号已有结果，直接返回，不开始新的写入。
2. 开始事务。
3. 按请求号插入一条「处理中」的幂等行；主键冲突则回滚并返回已有结果。
4. 条件更新月台日版本：`版本 = 版本 + 1` 且 `版本` 等于读到的值。影响行数为 0 则回滚，至多重试整个命令一次。
5. 读取该月台与候选时间窗重叠的已确认预约。
6. 有重叠则只把幂等结果写成冲突和下一空档，不插入已确认预约，然后提交。这次版本增量一并提交，竞争者的条件更新会失败并重试，重试时读到的仍是原来的已确认行。
7. 无重叠则把预约为已确认，写发件箱，幂等结果写成成功，提交。

只回滚、不记录冲突，不变量同样成立，因为重叠的依据是已经提交的预约行，不是版本号本身。本设计仍提交冲突的幂等结果，是为了同一请求号的重复调用不再占满 700 毫秒预算。变难的是：该请求号之后不能改时间再确认，必须用新请求号。这个代价写进契约。

事务外：报文适配在命令之前；发件箱投递在提交之后，由投递器按未投递行重试。投递器不打开预约对象。

### 4. 契约

ConfirmAppointment

- 调用方：预约入口的适配器，在报文已经译成命令之后。
- 前置：无。未知请求号表示新确认。
- 输入：仓库、月台、开始、结束、供应商、请求号。开始晚于或等于结束，返回非法输入，不写预约。
- 成功：返回预约号和已确认。提交预约行、发件箱行、幂等行、月台日版本加一。
- 错误：非法输入，不写。状态不允许，不用于本命令的新建路径。重叠，返回下一空档，不写已确认预约，写幂等冲突结果。版本在一次重试后仍失败，返回依赖冲突，调用方可换新请求号再试。四种错误都不抛业务异常。
- 幂等：请求号。重复的成功返回同一个预约号。重复的冲突返回第一次的下一空档，即使后来日历已变。这是第 3 节接受的代价。
- 副作用：成功时发件箱增加「预约已确认」，载荷只有预约号和仓号。与预约同一事务。
- 超时与重试：本单元对版本冲突重试一次。调用方不要对重叠结果自动重试同一请求号。

依赖：下一空档的计算是本模块只读查询，不锁卸货库。投递器是本进程稍后的读取，不是确认命令的依赖返回值。

NextFreeWindow

- 调用方：确认命令在重叠时；不对外单独承诺界面的交互步骤。
- 输入：仓库、月台、不早于某个时刻。
- 成功：返回一个与已确认预约都不相交的时间窗，长度等于本次被拒绝的窗。没有这样的窗时返回空，这是成功的一种，不是错误。
- 错误：月台不存在时返回非法输入。
- 幂等：无副作用，重复调用不写库。
- 事务：不开启写入事务，不更新版本行。它读到的是已提交的预约。确认命令若先抢到版本再调用它，读到的重叠与下一空档处于同一次事务的快照里。

### 5. 模式族

- 分解与规则：聚合是单张预约的状态。重叠用规格函数，确认和「下一空档」共用。放弃把日日历做成聚合。策略族没有第二个确认算法。状态用于已请求、已确认、已拒绝，不使用一串布尔值。
- 结构族和创建族：没有两个独立变化的维度，不用桥接。工厂不需要。
- 错误与并发：类型化结果。乐观版本加条件更新，版本行是月台日。放弃预约行上的版本作为唯一手段。发件箱按架构保留。放弃悲观锁整表。
- 数据映射：一次命令内身份映射只保证同一个预约号一个对象。重叠查询按月台和时间范围，要求该范围上有索引。没有索引则 S1 的 700 毫秒没有依据，这是敏感点。

### 6. 状态、数据、时序

| 当前 | 操作 | 守卫 | 下一 | 失败 |
| --- | --- | --- | --- | --- |
| 无此预约 | 确认 | 时间合法且无重叠 | 已确认 | 非法输入或重叠 |
| 已确认 | 同一请求号再次确认 | 幂等行已有成功 | 已确认 | 不新写 |
| 已确认 | 新请求号再次占用同一窗 | 重叠 | 保持 | 重叠 |

拒绝和取消不是本命令。它们以后要改状态时必须经过预约对象，不能让别的模块改表。

真相表：预约（预约号、请求号、仓、月台、开始、结束、状态）。并发令牌表：月台日（仓、月台、日期、版本）。发件箱：事件号、预约号、仓号、已投递标记。幂等：请求号、结果类型、预约号或下一空档。

```mermaid
sequenceDiagram
  participant cmd as 确认命令
  participant ver as 月台日版本
  participant cal as 预约表
  participant box as 发件箱
  cmd->>ver: 条件更新版本
  alt 影响行数为 0
    cmd-->>cmd: 回滚并至多重试一次
  else 抢到版本
    cmd->>cal: 按范围读已确认重叠
    alt 有重叠
      cmd-->>cmd: 提交冲突结果，不插入已确认
    else 无重叠
      cmd->>cal: 插入已确认
      cmd->>box: 插入未投递事件
      cmd-->>cmd: 提交
    end
  end
```

事务从条件更新开始，到插入发件箱之后提交。投递不在图里的事务内。

### 7. 走查

| 路径 | 检查与写入 | 事务 | 是否仍成立 |
| --- | --- | --- | --- |
| S1 成功 | 幂等未命中，版本加一，无重叠，写预约和发件箱 | 从版本更新到发件箱 | 成立的条件是范围查询有索引，且含一次重试仍小于 700 毫秒 |
| S1 重叠 | 版本加一后读到重叠，只写幂等冲突 | 同上，但不写已确认 | 成立。两个不同请求号的重叠者，只有一个能通过「无重叠」 |
| S1 并发 | 两个事务读到同一版本，只有一个条件更新成功 | 失败者整事务回滚 | 成立。失败者重试一次后会看见胜者的已确认行 |
| S2 崩溃 | 提交点之后进程消失 | 预约与发件箱已提交或都未提交 | 成立。投递器下次读取未投递行，不重新确认 |
| 重复请求号 | 命中幂等行 | 不进入版本更新 | 成立，且不第二次发件箱 |

### 8. 风险与证伪

- 敏感点：范围索引、重试次数、冲突结果被幂等键粘住。
- 取舍：把冲突结果写进幂等行，重复请求便宜，但同一请求号不能改时间再确认。
- 变难：版本行按日期拆开，跨日的时间窗必须更新涉及的每一天的版本，否则跨日重叠会漏。本例假设时间窗不跨日。若允许跨日，走查表的并发行失败，要在同一次事务里条件更新每一天。这是开放假设。
- 证伪：已确认预约中出现时间相交的一对；或确认接口在扣除入口之后的 95 分位超过 700 毫秒；或存在已确认预约但没有发件箱行。
- 没有现状代码。不编造现有的类。

## 例子二

**输入**

别搞版本行了，给预约表加个唯一索引不就行了。

**合格的回应**

理解成希望少一张表。唯一索引守得住的是完全相同的键，S1 的不变量是时间相交。8:00–9:30 和 9:00–10:00 可以同时通过唯一索引。所以不能用它替换月台日版本。

可以附加的、不替换版本的做法：没有。相等约束不加强重叠判断。若用户改为「预约只能整点且长度固定，重叠等价于开始时间相等」，唯一索引才够，版本行可以删，事务改成插入预约时捕获唯一冲突。在用户明确改不变量之前，版本行保留。故意不改发件箱与预约的同一事务。

## 已有代码

若代码里是「先 select 重叠，再 insert，没有条件更新」，体验式的读代码结论是：两个事务都能 select 到空再都 insert，S1 的走查行不成立。改法是补上月台日的条件更新，并把 insert 放在它成功之后、同一事务里。不要只在注释里写「注意并发」。读不到仓库时，不把这个缺陷说成现状。
