# 范围

没有这一页的产出，不准写类和表。

## 先钉死单元

写出这次设计的单元名称，以及它在架构里是什么：一个界限上下文、一个模块，或一个已经存在的包。写不出单元，说明还在做架构，改用 `/system-architecture`，不要在详细设计里从零切服务。

从架构交付里抄来本单元必须守住的场景，保留原来的响应度量。没有书面架构时，只列用户明确交给这个单元的行为，并把度量标成假设。不要补写一套结构轴和部署轴。

每条场景在本单元的落点用一句话说完：本单元负责其中哪一段响应。本单元不负责的那一段，写给相邻单元，不在这里设计对方的内部。

## 职责

用肯定句写本单元负责的不变量和操作。再用否定句写非职责。非职责至少包括：别的上下文的数据、界面流程、架构已经交给别的单元的失败域。

## 关注点清单

用户没提到的项也要过。每一项是「对应场景或操作」，或「不适用」加一句原因。

| 关注点 | 要落到的设计问题 |
| --- | --- |
| 操作 | 外部能调用哪些命令和查询；本单元消费或发出哪些消息 |
| 输入 | 哪些字段必填，哪些组合非法 |
| 输出 | 成功时调用方拿到什么，能否据此做下一步而不再猜 |
| 错误 | 每种失败的可见结果；哪些失败允许重试 |
| 幂等 | 同一次请求重复送达时，是否返回第一次的结果且不重复提交 |
| 不变量 | 哪条规则永远为真，由哪段代码在提交前检查 |
| 状态 | 有哪些稳定状态，哪些迁移是合法的 |
| 持久化 | 真相在哪些表或文档里，副本不是真相 |
| 事务 | 从哪一句开始，到哪一句提交；事务里有没有外部调用 |
| 并发 | 两个操作同时做时，谁会失败，失败后是否重试一次 |
| 锁的对象 | 版本或锁打在哪一行，而不是打在一句「加锁」上 |
| 时间 | 架构场景的延迟预算在本单元还剩多少，例如外部调用已占用的部分 |
| 观测 | 哪个计数能证明不变量被打破，例如双订次数 |
| 实现自由 | 私有函数怎么拆、局部变量怎么命名，写明不在本次约束内 |

传统详细设计说明书里的性能、输入输出、算法、出错、限制和验证，都要落在上表里。没有单独标题的，不算已经考虑过。
