# 设计模式

分层、管道、微服务、六边形、事件驱动、CQRS 在 [four-axes.md](four-axes.md) 里决定，不要在这里再投票一次。

扫描七个族。每一族在交付里只有两行以内：没有这类问题；或者选了谁、放弃了同族的谁、依据哪条场景。同族没被点名的模式不用逐个写否决。

一个模式若决定了发布单元、数据真相或跨进程一致性，停止把它当模式用，回到对应的轴。

## 创建

| 模式 | 采用 | 放弃 |
| --- | --- | --- |
| 工厂方法 | 创建哪一种由扩展方决定，调用方只依赖抽象 | 种类稳定，一个构造点就够 |
| 抽象工厂 | 一族对象必须配套出现，不能跨族混用 | 产品之间没有配套约束 |
| 生成器 | 同一过程要产出不同表示，或步骤多到不能放进构造函数 | 只有一种表示，字段也不多 |
| 原型 | 从现成实例复制比重新装配更正确或更省 | 复制会把不该共享的身份和状态带走 |
| 单例 | 这个进程里确要唯一入口 | 用它假装跨进程、跨节点只有一份真相 |

## 结构拆分

| 模式 | 采用 | 放弃 |
| --- | --- | --- |
| 适配器 | 外部接口改不了，要接进自己的抽象 | 边界是自己的，可以直接改 |
| 桥接 | 抽象和实现两个维度都会独立增加 | 只有一个维度在变 |
| 组合 | 部分与整体要递归，客户对叶子和容器用同一套操作 | 层次固定且很浅，递归只会绕 |
| 装饰 | 职责要在运行时叠加，子类组合会爆炸 | 组合在编译期就固定 |
| 外观 | 调用方不该知道子系统的进入步骤 | 调用方必须控制那些步骤 |
| 享元 | 大量对象的不变部分可以共享，可变部分在外部 | 对象数量不大，或没有可共享的不变部分 |
| 代理 | 要控制访问，同时让客户仍面对原有抽象：远程、延迟、权限、缓存 | 需要把两种抽象接在一起；那是适配器 |

## 行为协作

| 模式 | 采用 | 放弃 |
| --- | --- | --- |
| 职责链 | 处理者要到运行时才确定，请求可能沿链传递 | 处理者是固定的一个 |
| 命令 | 请求要入队、重试、撤销、审计或延后执行 | 调用完就结束，没有这些生命周期 |
| 解释器 | 文法小而稳定，规则要被业务人员配置 | 文法会变复杂；改用现成解析器，不要手写语法树 |
| 迭代器 | 要遍历集合，又不暴露存储方式 | 集合的内部结构本来就是接口的一部分 |
| 中介者 | 多个对象已经网状互调，协作规则要收拢到一处 | 对象只有一条清晰的调用链 |
| 备忘录 | 要在对象外保存和恢复状态，又不打开内部结构 | 直接持久化聚合更诚实 |
| 观察者 | 同一边界内，一处事实通知多个互不引用的对象 | 通知跨进程、要留存或独立部署；改到通信轴 |
| 状态 | 行为随生命周期阶段变化，条件分支已经在冒充状态机 | 只是一两个标志位 |
| 策略 | 同一职责有可替换算法，替换不改变调用顺序 | 分支是同一条规则里的条件 |
| 模板方法 | 骨架稳定，少数步骤变化，且接受继承 | 变化点更多，或要在运行时替换；看策略或装饰 |
| 访问者 | 对象结构稳定，加在结构上的操作会不断增加 | 结构本身经常变 |

## 领域模型

这一族只在结构或边界里确实有领域规则时扫描。

| 模式 | 采用 | 放弃 |
| --- | --- | --- |
| 聚合 | 用它划定一次事务里的一致性边界 | 把整个库做成一个聚合 |
| 实体 | 有连续身份，属性变了仍是同一个 | 没有身份，相等只看值 |
| 值对象 | 没有身份，替换整个值 | 还要跟踪它的生命周期 |
| 领域事件 | 模型内部已经发生、其他规则要得知的事实 | 用它代替通信轴上的集成事件而不加区分 |
| 领域服务 | 操作不属于任何一个实体或值对象 | 把它做成什么都往里放的应用服务 |
| 仓库 | 以聚合为单位取回，对领域伪装成集合 | 暴露查询语言给领域规则 |
| 工厂 | 创建聚合时的不变量复杂，不能靠构造函数看住 | 创建只是填字段 |
| 事务脚本 | 规则薄，一个请求就是一段过程 | 规则开始在多处复制 |
| 表模块 | 规则跟一张表走，数据集是主要抽象 | 规则是跨表的行为和生命周期 |
| 防腐层 | 上游模型会污染自己的语言，需要翻译层 | 上下游说的是同一种语言 |
| 开放主机与发布语言 | 多个下游依赖你，你要公布稳定的协议而不是内部模型 | 只有一个下游，而且你拥有它 |
| 共享内核 | 两个上下文必须共享一小块模型和发布节奏 | 共享部分会持续变大 |
| 客户-供应商 | 下游的场景能排进上游的计划 | 上游不会为下游改 |
| 遵奉 | 上游模型就该被服从，翻译没有价值 | 服从会使自己的场景无法表达 |
| 各行其道 | 两边没有需要对齐的场景 | 其实有共享的用户路径，只是没人愿意谈 |

## 数据访问与一致性

结构轴和数据轴已经定了真相在哪之后，才扫描这一族。

| 模式 | 采用 | 放弃 |
| --- | --- | --- |
| 工作单元 | 一次业务动作改多个对象，要一起提交或一起放弃 | 一次只改一个聚合，事务边界已经够用 |
| 身份映射 | 同一次工作里同一行不能变成两个对象 | 没有这个生命周期 |
| 数据映射 | 领域模型和表结构必须分开演进 | 两者本来就一致，映射只是样板 |
| 活动记录 | 模型接近表，一条记录知道如何保存自己 | 领域规则因此开始依赖表和连接 |
| 延迟加载 | 聚合图很大，场景只碰其中一截 | 它把远程调用藏进了领域规则 |
| 乐观离线锁 | 冲突少，用版本发现写冲突 | 冲突时代价是丢操作且不能接受 |
| 悲观离线锁 | 冲突时代价高，要先占住再改 | 锁的时长会跨人的思考时间，吞吐场景因此失败 |
| 发件箱 | 写库和发出消息必须同成同败 | 没有这个双写 |
| Saga | 一个业务动作跨多个数据所有者，用补偿或排序完成 | 用它代替本可以收进一个聚合的事务 |
| 幂等消费者 | 消息至少会到一次 | 把幂等当成「再查一次数据库」却没有幂等键 |

## 集成与弹性

通信轴或部署轴让一块会独立失败时扫描。消息通道、路由器、转换器、端点、点对点、发布订阅、竞争消费者、死信通道，只在通信轴已经是消息时扫描；否则这一组整组不适用。

| 模式 | 采用 | 放弃 |
| --- | --- | --- |
| 点对点通道 | 一条消息只该被一个消费者处理 | 多个消费者都要看见 |
| 发布订阅通道 | 多个消费者独立反应 | 工作不能被做两次，却没有分区或竞争规则 |
| 消息路由器 | 目的地由消息内容或规则决定 | 只有一个固定目的地 |
| 消息转换器 | 两边的契约不同，转换不属于任何一边的模型 | 转换里开始写业务不变量 |
| 竞争消费者 | 一组工作者分担同一通道，处理可以并行 | 顺序是场景度量的一部分，又没有分区键 |
| 死信通道 | 失败消息不能堵回业务通道 | 失败后只能由原发送方处理 |
| 断路器 | 下游持续失败时要快速失败，避免耗尽自己 | 失败是个别请求，重试就够 |
| 隔舱 | 一种依赖或一种租户的失败不能占满全部容量 | 只有一个依赖、一个容量池 |
| 超时 | 没有时限的等待会违反场景度量 | 工作本来就是长任务，超时应放在任务自己的期限上 |
| 重试 | 失败可能短暂消失，且操作幂等或可识别重复 | 对非幂等操作盲目重试 |
| 限流 | 要在过载时拒绝一部分，保护响应度量 | 用限流掩盖容量没按场景设计 |
| 网关 | 外部入口要收拢认证、路由和协议 | 内部服务互相调用也绕进同一个网关，耦合因此集中 |
| BFF | 不同调用方的场景形状不同，后端聚合会互相拖累 | 只有一种客户端 |
| 边车 | 网络、身份或观测要跟进程一起走，又不能写进业务模型 | 它变成第二条业务路径 |
| 绞杀者 | 旧边界还要继续运行，新路径按场景逐条替换 | 没有旧系统，或一次性切换才是约束 |

## 演进

| 模式 | 采用 | 放弃 |
| --- | --- | --- |
| 绞杀者 | 见上一族。替换路径按场景切 | 没有可并列运行的旧路径 |
| 防腐层 | 新模型要在旧模型还活着时保持干净 | 替换会在一个发布里完成 |
| 分支抽象 | 要在继续发布的同时换掉内部实现 | 调用点只有一个，直接替换更清楚 |
