# 两份文档

架构这一轮要交两份文件，都写在产品仓库的 `docs/`。已有同名文件就更新，不另起一套。聊天里只给路径和被选定的框架，不把两份全文再贴一遍。

取舍、四轴、视图和决策记录是写进这两份文件的材料，不是第三种自拟提纲。

## 框架设计

文件：`docs/框架设计.md`。

它回答系统骨架：和外部是什么关系、技术路线为什么是这条、逻辑上分成哪几块、物理上落在哪。不写每个模块的输入输出表，那是概要设计。

1. 简介：目的、范围、术语、参考资料。
2. 设计方案：与外部系统的关系；选型标准；至少两个备选方案和否决理由；设计约束（标准、硬件、技术、人员与成本）；选定的平台和技术架构。
3. 系统架构：逻辑架构（依赖方向）；物理架构（节点、网络、进程）；功能分解到子系统，不进到子程序；采用的架构风格，以及它没有覆盖的轴。

四轴的选择和否决写在「备选方案」和「系统架构」里。C4 上下文图、容器图、部署图放在逻辑架构或物理架构，同一张图不重复贴。质量场景和证伪条件写在选型标准旁，用来说明为什么否决另一个方案。

## 概要设计说明书

文件：`docs/概要设计说明书.md`。章节按 GB/T 8567-1988 第 11 章，标题不要改名、不要并成「决策记录」。

1. 引言：编写目的、背景、定义、参考资料。参考资料里写明框架设计文件。
2. 总体设计：需求规定（主要输入输出和性能，不重写需求说明书）；运行环境；基本设计概念和处理流程（模块之间的流程图）；结构（模块标识符、功能、谁控制谁）；功能需求与程序的关系（矩阵：每条功能落在哪个模块）；人工处理过程；尚未解决的问题。
3. 接口设计：用户接口只列命令和系统回答，不画界面稿；外部接口（软硬件、支持软件）；内部接口（模块之间传递什么，不写模块内部算法）。
4. 运行设计：运行模块组合；运行控制；运行时间（哪种运行占什么资源）。
5. 系统数据结构设计：逻辑结构（名称、数据项、相互关系）；物理结构（存储、访问、索引）；数据结构与程序的关系。
6. 系统出错处理设计：出错信息一览；补救（后备、降效、恢复）；系统维护设计（检测点和专用模块）。

概要设计停在模块边界。确认预约如何抢版本、类怎么拆，写进详细设计说明书，不写在这里。

没有材料的小节写「不适用」和原因，不删标题。
