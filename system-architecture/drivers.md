## 质量场景

每条靠前的场景都写成：

- 来源：谁或什么触发
- 刺激：发生了什么
- 环境：正常、峰值、故障、发布中
- 制品：被刺激的是哪一块
- 响应：系统表现出什么
- 响应度量：时间、比率、恢复时限、数据差异窗口、人工步骤数。必须有数或有明确的阈值假设

效用树按质量属性分组。每条标重要性（高、中、低）和实现难度（高、中、低）。重要性高且难度高的场景，决定后面的取舍，不得埋在附录里。

质量属性至少检查这些，没有的分组写「本次没有」：性能、可用性、可修改性、安全性、可测试性、易用性（仅当它约束架构，而不是界面）、互操作性、可移植性、成本。

## 关注点清单

用户没提到的项也要过。每一项的结论是「对应场景编号」，或「不适用」加一句原因。

| 关注点 | 要问清的结构问题 |
| --- | --- |
| 功能与语言 | 哪些规则和词汇不同，因而不能放进同一个模型 |
| 数据 | 谁拥有数据，一致性窗口，保留期限，谁可以复制 |
| 通信 | 调用方是否要等结果，耦合发生在编写时还是运行时 |
| 失败与容量 | 哪一块坏了其余还能做什么，峰值比日常大多少 |
| 安全 | 信任边界在哪，谁认证，谁授权，什么要留痕 |
| 观测与操作 | 怎样知道场景的响应度量正在失败，谁在值班 |
| 演进 | 未来最可能改变的两件事是什么 |
| 团队与发布 | 谁拥有哪一块，一块能否单独发布 |
| 成本 | 可以接受的运行单元数量和运维复杂度 |
| 合规 | 领域有监管、审计或地域限制才展开，否则写不适用 |

约束和假设分开。约束是已经不能选的东西，例如必须沿用的数据库、团队规模、交付期限、法规。假设是暂时当成真的度量或事实。假设被推翻时，要能指出哪条决策作废。
