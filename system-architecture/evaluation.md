# 决策与反思

## 决策记录

每条改变边界、四轴或跨团队契约的选择写一条。模式只在它形成契约或一致性规则时单独记录。

- 标题
- 状态：提议、已接受、被取代
- 上下文：指向场景编号和约束，不重抄全文
- 方案：至少两个，其中一个可以是现状
- 结果：留下哪一个
- 后果：哪条场景变容易，哪条变难
- 证伪：出现什么度量或什么变化就说明该重开这条决策

没有后果和证伪的记录，等于没做决策。

## 走查决策

对重要性高的场景各做一次，不要对形容词做：

1. 写出承担这条响应的结构机制，指到具体单元，不写「通过解耦」。
2. 敏感点：哪个参数一变，响应度量就会失败。例如一致性窗口、超时、分区键、发布单元的大小。
3. 取舍点：提高这条场景时，哪一条别的场景变差。两全其美说明还没取舍。
4. 风险或非风险。风险必须对应一个可能达不到的响应度量。
5. 风险若能靠改边界、改轴或改模式消除，就在本轮改。若接受它，写进假设，并指向会作废的决策。

可演进性或运行度量若排在前面，给一条适应度条件：用什么测试、指标或评审规则发现架构正在偏离。给不出条件，说明场景的响应度量还是形容词，回到驱动。

## 怎样算反思

对照现状或上一轮，只记录改变了响应度量、边界、一致性窗口或失败域的修改。

下列不算完成反思：重画布局、更换同义的风格名词、补一篇原则、在风险列表里加「需要进一步设计」却不改结构。

内部循环最多两遍。第二遍之后仍有靠前场景走不通，或仍有无主的风险，就在交付的第 8 节写明开放项，交给用户决定接受还是改驱动。

用户要求修改时，先判断变化落在哪条场景、哪一轴、哪张图。只重开这些。走查表里受影响的行必须重写。被取代的决策把状态改成被取代，不删掉，以免下一轮忘记代价。
