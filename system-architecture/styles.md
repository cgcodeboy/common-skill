# 四轴取舍

每一轴留下一个选择。否决项至少一条，并指向 [drivers.md](drivers.md) 里的场景或约束。领域语言的切分见最后一节，它发生在四轴之前，但不取代四轴。

## 先切边界

多个子域的规则和语言会独立变化时，按界限上下文切开。只有一个模型和一种变化节奏时，不要制造上下文。

上下文之间的关系只选一种主关系：共享内核、客户-供应商、遵奉、防腐层、开放主机加发布语言、各行其道。大泥球只能用来描述现状，不能当作目标。

## 结构轴

运行单元和代码边界如何切。

| 选择 | 留下 | 否决 |
| --- | --- | --- |
| 分层单体 | 一种变化节奏，一个发布单元，调用链短 | 各层变化频率已经不同，分层只是增加传递 |
| 模块化单体 | 需要模块边界和依赖纪律，但仍要一起发布、一起一致 | 模块必须独立扩容或独立失败 |
| 六边形 / 整洁 / 洋葱 | 领域规则必须在没有入口和基础设施的情况下被验证 | 没有可隔离的领域规则 |
| 服务化 | 按业务能力切开所有权，发布单元仍可以比较大 | 团队、数据和故障域都已经要求独立 |
| 微服务 | 独立部署、独立数据、独立故障域，且团队能拥有这些单元 | 一致性必须跨服务即时完成，或团队守不住多个运行单元 |
| 微核加插件 | 核心稳定，周边能力会由不同节奏追加 | 插件之间有丰富的共享不变量 |
| 细胞 / 空间划分 | 要按数据或租户把故障和容量切开 | 切分之后跨细胞协作才是主路径 |

## 通信轴

一块如何把工作交给另一块。

| 选择 | 留下 | 否决 |
| --- | --- | --- |
| 同步请求-响应 | 调用方要在同一次操作里得到结果 | 调用链变长，或被调用方的故障会直接拖垮调用方 |
| 异步命令 | 可以晚一点做完，但要明确谁负责完成 | 调用方没有完成回执就无法继续，又不想引入状态查询 |
| 事件通知 | 事实发生后，多个消费者独立反应，事件本身很薄 | 消费者没有事件就无法工作，却不许再查询 |
| 事件携带状态 | 消费者不能回查生产者 | 事件变成一份会过期的隐藏数据库 |
| 批处理或文件 | 节奏是窗口而不是单次请求，吞吐比延迟重要 | 场景度量是秒级响应 |
| 共享数据库 | 只作为现状或受约束的过渡 | 把它当成目标集成方式，同时又要求独立变化 |

事件通知和事件携带状态都是事件驱动。选定之后写明是哪一种。

## 数据轴

真相在哪，读和写是否同一模型。

| 选择 | 留下 | 否决 |
| --- | --- | --- |
| 单一模型，即时一致 | 读写同一形状，场景不能接受中间状态 | 读模型和写模型的规模、形状或变化已经分开 |
| 上下文拥有自己的数据 | 边界已经切开，跨边界可以接受一致性窗口 | 一个事务必须同时改两个上下文的不变量 |
| CQRS | 读和写的模型、路径或规模不同 | 只是同一个模型的两个接口 |
| 事件溯源 | 事实序列本身要审计、重放或重建状态 | 只是需要一条历史日志，状态仍是真相 |
| 管道或分析模型驱动操作 | 决策来自数据产品或离线/流式计算结果 | 不变量主要是在线事务里的领域规则 |
| 数据网格 | 多个域各自把数据当产品发布，消费者不回查对方的库 | 只有一个域、一份数据 |

## 部署轴

进程落在哪，失败域如何与结构对应。

| 选择 | 留下 | 否决 |
| --- | --- | --- |
| 单进程 | 一个失败域就够，运维成本要低 | 一部分必须单独扩容或单独崩溃 |
| 同节点多进程 | 要隔离故障，但仍在同一台机器的可用性里 | 节点故障不能影响全部能力 |
| 容器编排 | 多个运行单元，要调度、扩容、滚动发布 | 运行单元只有一个，编排只增加平台成本 |
| 平台函数 | 负载起伏大，按调用付费，冷启动能放进场景度量 | 长连接、稳定低延迟或本地状态是场景要求 |
| 边缘加中心 | 延迟或地域要求计算靠近来源，真相仍要汇合 | 边缘和中心的数据冲突场景无法定义 |

结构轴选了微服务或细胞，部署轴仍要单独写。独立部署不等于已经选择了编排或地域。
