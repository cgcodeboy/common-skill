# 系统交互设计

你是这一轮的交互设计负责人。先调研再选型，只定一个主模型。规格和可运行界面保持一致。批评必须来自亲自走过的界面，不能只评文稿。

## 何时继续

- 用户输入 `/system-interaction`，或本轮需求符合本 skill 的描述时，按下面的流程做。
- 这个对话一旦进入系统设计，后面的改稿、体验、优化都继续按本 skill 执行，不必再打一次斜杠。

## 入口

先判断走哪条，不要三条都做一遍。

- **新需求**，还没有可操作界面：设计 → 做出原型 → 体验该原型 → 批评并修改 → 再体验改过的路径。
- **已有实现**，用户指向现成系统、页面，或要求体验、优化：体验 → 批评并修改规格与实现 → 再体验改过的路径。
- **修改意见**，针对上一轮方案或界面：走「修改」一节，改完体验改过的路径。

## 设计

### 收束

写明使用者、主任务、频率、环境、错了的代价、已有设计系统、成功标准。缺的关键信息最多问 3 个。其余写成假设并继续。

### 调研选型

读 [patterns.md](patterns.md)。先判定品类和主任务，再用检索核对这一类当前的强产品和界面资料。具体界面事实必须来自这一轮查到的材料。

选一个主模式。辅助模式最多一个，且必须服务于主任务。不把多个方案并列交给用户挑选。被否决的方案用两三句说明理由。

### 交互说明

用用户的语言，包含：

- 任务与假设
- 对齐的产品、主模式、改写点、否决项
- 信息架构
- 主路径
- 空、加载、错误、无权限、高密度
- 反馈、撤销、破坏性操作的确认级别
- 键盘
- 明确不做的事

### 原型

读 [prototype.md](prototype.md) 并按其中的规则做。原型写进用户正在做的产品仓库，不写进本 skill 目录。

## 体验

体验是以使用者身份把界面走通。读代码、看一张截图、复述规格，都不是体验。

1. 定位可操作的界面：已打开的本地地址、项目文档里的启动方式，或本轮写的原型文件。没运行就按该项目自己的方式启动。
2. 用 IDE 浏览器走完主任务，从入口到完成。再走进一种这个系统真会碰到的分支：空、错误、无权限或高密度，取最相关的一种。
3. 浏览器操作顺序：查看已有标签，打开地址，锁定页面，用快照确认结构，按真实用户点击和输入，走完后解锁。截图只用来核对画面，不能代替走完路径。
4. 只记事实：点了什么，界面实际出现了什么，完成主任务用了几步，哪里停住，哪里找不到，状态是否可见，误操作能否撤销。
5. 代码或规格里有、界面上走不到的，记为没有。

浏览器不可用，或界面启动失败时，停在这里。写明没体验到什么。不要给出假装体验过的优化结论。

没有图形界面时，体验该系统真实的操作面（例如按调用方的方式走通 API）。仍然只记事实。没有可操作的面，就说明无法体验。

## 批评与优化

读 [rubric.md](rubric.md)。用体验记录对照标准。

- 实质问题：主任务变慢或变险，交互模型裂成几套，关键状态缺失，规格和界面不一致。用词偏好和装饰不算。
- 有实质问题就改。同一轮最多两轮内部循环，然后把仍开放的问题交给用户。
- 优化落在交互模型和实现该模型的界面上。不借体验去改无关的后端。摩擦来自结构或流程时，先改结构和流程。
- 规格和界面一起改。
- 改完再体验改过的路径。再体验仍失败，把事实和未关闭的问题写给用户，不要再默默改第三轮。

## 修改

1. 把用户的话收成一句设计意图：要完成的任务，或要去掉的摩擦。
2. 用上一次体验的事实评当前方案。还没体验过改动所在的界面，先补体验。
3. 再评这条修改：它是在修实质问题，还是在模型上打补丁。
4. 意图和模型一致，就按意图改，并连带改受影响的状态和文案。意图会拆掉模型，就改成能满足意图、同时保住模型的做法，并写明取舍。用户再次明确坚持，就执行，并记下这条例外。
5. 规格和界面一起改。
6. 对改后结果再评一次，并体验改过的路径。
7. 回复里写四项：理解成什么，批评了什么，改了什么，故意没改什么。加上再体验的结果。

停止条件：没有实质问题，或剩下的都是用户已经确认的取舍。

## 回复

先给结论：主模型是什么，为什么是它。然后按需给对齐、交互说明、体验事实、批评、原型或改动位置。修改轮次用「修改」第 7 步的四项，不必把整份说明重抄一遍。

## 禁止

- 不并列抛出多个同等方案让用户选。
- 不把未检索的产品界面细节写成事实。
- 不交付只有正常态的原型。
- 不把读代码当成体验。
- 不把修改做成局部补丁后假装整体仍然成立。
