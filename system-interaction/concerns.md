# 任务与关注点

没有这一页的产出，不准画界面。

## 任务场景

每条靠前的任务都写成：

- 谁：具体角色，不写「用户」
- 触发：什么事情把他带到这里
- 环境：高峰、第一次、中断后回来、出错之后、权限不够
- 完成标准：步数、时间、能否撤销、是否必须看见某个状态。必须有数或有明确的阈值假设

至少写出一条主任务和一条失误或异常任务。重要性高的任务决定三轴，不要埋进附录。

同时写清使用频率和失误代价。高频专家工具和偶尔来一次的审批，不是同一套交互。代价高的操作不能靠颜色深浅来防止。

## 关注点清单

用户没提到的项也要过。每一项的结论是「对应任务编号」，或「不适用」加一句原因。

| 关注点 | 要问清的界面问题 |
| --- | --- |
| 对象 | 人以为自己正在操作的东西是什么，一个还是一批 |
| 语言 | 界面用领域里的词，还是用软件内部的表名和状态码 |
| 频率 | 同一动作每天几次。超过多次仍要点很深的菜单，就是结构问题 |
| 密度 | 一屏要比较多少条才做得出决定 |
| 失误 | 做错时能否撤销，撤销窗口有多长；不能撤销的，确认发生在动作之前还是要键入对象名 |
| 并发 | 别人改了同一条时，当前的人看见什么 |
| 权限 | 不能做的操作是隐藏、禁用，还是做了才报错。禁用时能否知道原因 |
| 中断 | 做到一半离开，回来时筛选、草稿和滚动位置还在不在 |
| 反馈 | 成功、失败、进行中分别出现在动作旁边，还是消失在角落 |
| 键盘 | 专家是否必须离开键盘才能完成主任务 |
| 无障碍 | 焦点顺序是否跟主路径一致，状态是否只靠颜色区分 |
| 已有界面 | 产品里已经有的密度、组件和词要不要沿用 |

环境假设分开写。例如「高峰每分钟处理 20 条」「调度已经认识月台这个词」。假设被推翻时，要能指出哪一轴作废。
